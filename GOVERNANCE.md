# Questlock governance

Questlock is an independent, maintainer-led open-source project. Its current
maintainer is listed in [MAINTAINERS.md](MAINTAINERS.md). Participation is open to
individuals and organizations under the [MIT license](LICENSE) and
[Code of Conduct](CODE_OF_CONDUCT.md).

## Proposing and deciding changes

Use public issues for proposals and pull requests for implementation. Explain
the problem, alternatives, compatibility impact and evidence. Substantial
features and dependencies should start with an issue so contributors can agree
on scope before implementation. Security reports follow [SECURITY.md](SECURITY.md)
instead of public discussion.

The maintainer seeks agreement in public and records the rationale when
alternatives remain. The maintainer makes the final decision on scope,
compatibility, merging and releases. Review comments and passing automated
checks inform that decision; neither is permission to publish on someone
else's behalf.

## Maintainer responsibilities

- Review contributions for correctness, documented limits, tests and compatibility.
- Keep security reports, credentials and private task content out of public issues.
- Preserve published releases and document migrations instead of rewriting history.
- Distinguish measured results from hypotheses and retain failed evaluations.
- Arrange independent review for substantive releases and disclose material limits.
- Treat contributors respectfully and apply the Code of Conduct consistently.

There is one maintainer today. The project welcomes sustained contributions
from other people and organizations. Additional maintainers can be proposed in
a public issue after a record of useful contributions and review. The proposal
should describe responsibilities, the nominee's agreement and the access
required. The existing maintainer records the decision, updates MAINTAINERS.md
and grants only the access needed. Inactive maintainers may step down; any
change is recorded publicly without removing attribution for earlier work.

## Conflicts and changes to governance

Explain disagreements in the relevant issue or pull request and focus on
evidence and user impact. Conduct concerns follow the private-contact process
in the Code of Conduct. When a concern involves the only maintainer, another
trusted person may be asked to review it with the reporter's consent; the
project does not currently provide an independent standing appeals body.

Propose governance changes through a public pull request. Affiliation with a
foundation, a license change or a transfer of project assets requires an
explicit maintainer decision and any required approvals; a directory listing
does not establish those changes.
